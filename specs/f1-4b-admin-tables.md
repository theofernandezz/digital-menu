# Spec: F1-4b — `/admin/tables`: list, create, open, close

Mode: spec-first (backend then ui then testing, in sequence, so it has real dependencies between steps). Reviewed by the owner only after the fact, by their explicit choice for this one. F1-4a (tables identified by `table_number`) is already applied locally and on production.

## Outcome
The signed-in owner opens `/admin/tables` (new "Mesas" entry in the admin nav and a card on the admin home) and can: see their tables ordered by number with whether each is open or closed; create a table by typing its number; open a table (start a session) and close it; and see, for every table, its absolute link `<origin>/t/<token>` to open in the browser (the future QR will encode exactly that URL; in development the owner clicks it, nobody scans anything). Everything in the UI is in Spanish, code in English.

## Scope
- **domain/**: entity `DiningTable` (`id`, `restaurantId`, `tableNumber`, `qrToken`, `isOpen`), validating `tableNumber` as an integer 1-999 the way `Category` validates its fields; errors in a new `domain/errors/table-errors.ts` as `DomainError` subclasses: `InvalidTableNumberError`, `AlreadyOpenError`, `DuplicateTableNumberError`. Reuse the existing `NotFoundError` and `UnauthorizedError`.
- **application/**: port `DiningTableRepository` (list by restaurant ordered by number with open state; find by id; create; open session; close session), a Zod schema for the create input, and four use cases with the `AuthProvider` (same shape as the catalog ones): `list-tables`, `create-table`, `open-table`, `close-table`, each with a unit test and a fake repository added to `application/__tests__/fakes.ts`.
- **adapters/driven/supabase/**: `SupabaseDiningTableRepository` talking to `dining_tables` and `table_sessions` directly (the owner's RLS policies already allow it; no RPC, no migration), plus a unit test for its error mapping and an integration test against the local Supabase.
- **composition/**: add the four use cases to `composition/ordering.ts` and to `OrderingUseCases`, so `app/` reaches them through `getUseCases().ordering`.
- **app/admin/tables/**: `page.tsx` (server component), `actions.ts` (Server Actions), `table-form.tsx` (create), `table-list.tsx` and a client component for the row buttons, following the patterns of `app/admin/categories/` and `app/admin/items/availability-toggle-form.tsx` (`useActionState`, `toast`, `toFormErrors`, view models in `app/admin/view-models.ts`, reuse the atoms `Button`, `Input`, `Label`, `FieldError`, `Rule`). Entities never cross to client components: map to plain view models. The token stays on the server: the page builds the absolute link and only the link goes to the client.
- **Nav**: `app/admin/admin-nav.tsx` and the card list in `app/admin/page.tsx` get "Mesas".
- **Tests**: unit tests for use cases, adapter mapping, actions and the pure link builder; component tests for the list and the form where the repo's existing component tests give a pattern; integration test; one Playwright spec `e2e/admin-tables.spec.ts` for the whole flow through the browser.

## Out of scope
- Editing or deleting tables, QR image generation, showing when a table was opened (the model has no timezone; a server-rendered clock time would be wrong on Vercel), any view of orders or order history, the `/t/[token]` page, the cart, `get_table_status` in the app (F1-6), any migration.
- Editing `docs/` (the orchestrator updates them), editing any existing migration, changing existing tests.
- No new dependency unless a criterion cannot be met without it (then stop and report).

## Constraints
- **Authorization.** Every use case first requires a signed-in user (`getCurrentUserId`), then asserts ownership of the restaurant. Open and close take only the table id from the caller: the use case loads the table, and the restaurant used for the ownership check and for the new session's `restaurant_id` is the **table's own**, never a value from the client. A caller-supplied `restaurantId` on open or close is ignored. A table that does not exist or that the caller cannot see (RLS) gives `NotFoundError`, indistinguishable from each other.
- **Create** takes `restaurantId` from `getMyRestaurant` in the action (like `createCategoryAction`), and `tableNumber` from the form as a string coerced to an integer; anything outside 1-999 or non-integer is rejected before the repository is called.
- **Errors.** In the adapter: Postgres `23505` on `dining_tables` maps to `DuplicateTableNumberError`, on `table_sessions` to `AlreadyOpenError` (the one-open-session unique index makes this race-safe); any other error is `SupabaseAdapterError`, never shown. In the actions: `AlreadyOpenError` shows "La mesa ya está abierta", `DuplicateTableNumberError` shows "Ya existe una mesa con ese número", a Zod error shows its field error, anything else shows one generic Spanish message and is logged server-side (`toFormErrors`). Raw error text never reaches the client.
- **Close is idempotent:** closing a table with no open session succeeds and changes nothing. Open on an open table fails with `AlreadyOpenError`.
- **Link.** Built server-side as `<origin>/t/<token>`; origin from the request headers (`x-forwarded-proto` and `x-forwarded-host`, falling back to `host`; `http` for localhost, `https` otherwise) in a small pure function with a unit test. Shown as a real link (`target="_blank"`, `rel="noreferrer"`) with the URL as its text. Until F1-6 the target answers 404; that is expected.
- After each action, `revalidatePath("/admin/tables")`. Buttons are disabled while pending.
- Boundaries: `app/` imports no adapter and no Supabase SDK (ESLint enforces it). Hexagonal style, no `any`, no enums, Zod on all input, kebab-case files. No `useEffect` for data fetching. The page is protected by the existing admin layout guard (do not add a second one).
- Test hygiene: the integration tests and the e2e run against a database seeded with tables 1-3 (and `table-access` uses 900-903 in that restaurant). New tests must use numbers outside those, clean up what they create, and be repeatable (the integration suite and the e2e must pass twice in a row on the same database).
- Sequence for the implementer roles: `backend` builds domain to composition plus `actions.ts` and their tests and reports the exact exported names and signatures; `ui` then builds the page and components on top of those names (it has no shell, so it cannot run anything); `testing` then writes and runs the e2e and runs all gates, fixing only test files. If a gate fails because of production code, it reports instead of patching.
- If anything is ambiguous and not covered here: stop and report, do not guess. Existing tests are never edited to pass.

## Acceptance criteria
- [ ] **List.** For the signed-in owner the list returns their tables ordered by number with `isOpen` correct for tables with and without an open session, and never another owner's tables (integration test with a second user).
- [ ] **Create.** Numbers 1 and 999 are accepted; 0, 1000, 1.5 and non-numeric input are rejected before the repository is called (unit); a duplicate number in the same restaurant gives `DuplicateTableNumberError` (integration) and, through the action, the message "Ya existe una mesa con ese número".
- [ ] **Open.** Opening a closed table makes it open; opening it again gives `AlreadyOpenError` and the message "La mesa ya está abierta". The stored session's `restaurant_id` is the table's, and a `restaurantId` passed by the caller is ignored (unit test with a foreign id, integration test on the stored row).
- [ ] **Close.** Closing an open table makes it closed; closing a closed table succeeds and changes nothing.
- [ ] **Authorization.** With no signed-in user, all four use cases fail with the unauthorized error before touching the repository (unit). A second signed-in owner cannot list, open or close the first owner's tables: open and close give `NotFoundError` and no row changes (integration).
- [ ] **No leaks.** An unknown error in any action becomes one generic Spanish message with no raw text, and the error is logged (unit test on the actions).
- [ ] **UI.** `/admin/tables` shows the list (number, "Abierta" or "Cerrada", the absolute link), an empty state when there are no tables, the create form and the open or close button per row, matching the look and conventions of the other admin pages; the nav and the home card have "Mesas". The link builder has a unit test for localhost with `http`, a production host with `https`, and the forwarded-header precedence.
- [ ] **End to end.** The Playwright spec logs in as the seeded admin, creates a table with a number unused by the seed, sees it "Cerrada" with a link whose path is `/t/<its token>`, opens it (sees "Abierta"), closes it (sees "Cerrada"), and tries to create the same number again and sees the duplicate message. It passes twice in a row locally, or, if the local Docker and app setup makes that impossible, the report states exactly why and the spec is still written and typechecked so CI can run it.
- [ ] **Gates.** `pnpm exec tsc --noEmit`, `pnpm lint` (0 errors), `pnpm test`, `pnpm test:integration` twice in a row, and `pnpm build` pass; no existing test was edited or weakened; no file under `supabase/migrations/` or `docs/` changed.
